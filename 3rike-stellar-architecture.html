1. System Architecture Overview

3riKE is a rider- and investor-facing platform. Riders lease-to-own electric three-wheelers with weekly USDC payments and build a portable, mobility-based credit identity; investors fund those vehicles as fractional real-world assets and receive automated, transparent yield. Every unit of value, ownership, and repayment settles on Stellar — chosen for sub-cent fees, ~5-second finality, native USDC, and Soroban programmability that makes ownership and cash-flow verifiable and composable rather than opaque.

The platform is a React/Vite PWA (rider + investor portals), a Node.js/TypeScript API with a Postgres ledger-index, a Sovereign Key Security Layer (client-side AES-256-GCM, with an optional passkey smart-wallet path), and a set of Stellar integration providers: Horizon + Soroban RPC, the 3riKE Soroban contract suite, Africa-facing anchors (SEP-6/24), Bridge (Stripe) stablecoin orchestration, the Reflector oracle, and DeFi composability (DeFindex, Soroswap, Blend).

3. Non-Custodial Wallets & Sponsored Onboarding

The largest barrier for non-crypto riders is wallet setup and gas. 3riKE eliminates both by creating and funding the user's Stellar account for them, with zero XLM ever required.

3.1 Account creation via Sponsored Reserves (CAP-33)

Stellar requires every account to hold a minimum XLM base reserve, plus an additional reserve per subentry (each trustline, for example). A first-time rider owns no XLM, so 3riKE's sponsor account absorbs those reserves. A single atomic transaction opens with BeginSponsoringFutureReserves, runs CreateAccount at a zero starting balance, adds ChangeTrust lines for USDC and the 3RIKE-SHARE asset, and closes with EndSponsoringFutureReserves. The rider co-signs to prove key ownership while the sponsor pays every reserve. The result: a live account holding USDC and zero XLM — with sponsored reserves reclaimable if the account is ever closed.

3.2 Absolute gas abstraction via Fee-Bump transactions (CAP-15)

Every user action — pay a lease, buy shares, save, claim yield — is signed locally by the rider, then wrapped in a fee-bump envelope whose fee source is 3riKE's sponsor wallet. The sponsor signs the outer envelope and submits; the network deducts the fee from the sponsor. The rider spends zero XLM on every transaction, and 3riKE can optionally meter an equivalent micro-fee in USDC within the same operation set. Riders never learn what "gas" is.

3.3 Sovereign key security

The user's key is derived and protected client-side: a 6-digit PIN is stretched with PBKDF2-HMAC-SHA256 (600,000 iterations) into a 256-bit key that encrypts the seed with AES-256-GCM (authenticated). Only the encrypted blob, IV, and salt are ever stored. Signing decrypts strictly in-memory; the seed never persists to disk or transits the network.

3.4 Optional upgrade — Passkey smart wallets (seedless)

For a truly seedless experience, 3riKE can deploy a per-user passkey smart wallet as a Soroban custom account. Since Protocol 21, Soroban verifies secp256r1 (P-256) signatures natively — the exact curve used by WebAuthn passkeys. A device-bound biometric passkey authorises contract invocations through the account's custom authorization entrypoint, with 3riKE as an optional policy/recovery signer. This yields phishing-resistant onboarding with no PIN and no seed, ideal for mobile-first, low-literacy users, while the encrypted-key path remains a fallback.

4. Soroban Foundations

Before the product contracts, four Soroban capabilities underpin the whole design.

USDC inside Soroban — the Stellar Asset Contract (SAC)

Classic Stellar assets become callable from smart contracts through the Stellar Asset Contract — a canonical token contract that wraps issued USDC and exposes the standard token interface. Every 3riKE contract moves value by invoking the USDC SAC, so contract holdings, escrow balances, and user wallets are the same asset, fully interoperable with the rest of the Stellar economy. No wrapped or synthetic USDC is introduced.

Deterministic state & archival (storage tiers + TTL)

Soroban exposes three storage tiers, and 3riKE maps them deliberately: Instance storage holds small contract-global config (asset addresses, admin, per-vehicle pool parameters); Persistent storage holds long-lived, high-value state (per-investor share balances, lease ledgers, credit records); Temporary storage holds ephemeral data. Persistent and instance entries carry a Time-To-Live and are archived if left untouched. 3riKE extends TTLs on active leases and open positions and restores archived entries on access — keeping ledger rent predictable while guaranteeing the chain stays the single source of truth.

Explicit, composable authorization

Every state-changing entrypoint asserts authorization on the acting address, and cross-contract calls carry scoped authorization trees: when lease_to_own invokes yield_distributor and credit_registry inside one rider payment, the rider's single signature authorises exactly that composed set of actions — and nothing more. Passkey smart wallets plug into the same framework as custom accounts. This makes multi-contract flows atomic and least-privilege.

Events & indexing

Contracts publish structured events on every meaningful change — payment made, ownership advanced, yield distributed, delinquency flagged. 3riKE's indexer subscribes over Soroban RPC and projects events into Postgres, so the app serves instant portfolio, ownership-progress, and activity-feed reads while the ledger remains authoritative.

5. The 3riKE Soroban Contract Suite — core engine

Five composable contracts turn a physical tricycle into a transparent, financeable, co-owned asset.

5.1 tricycle_vault — RWA tokenization & fractional shares

Registers one on-chain asset record per real vehicle (make, model, VIN, price, battery/range metadata) and issues fungible ownership shares conforming to the SEP-41 token interface. Because shares are a standard token, investor ownership is portable and composable — any wallet, explorer, or protocol on Stellar can read it. Investing pulls USDC (via the SAC) and mints shares to the investor; balances live in persistent storage keyed by vehicle.

5.2 lease_to_own — escrow & milestone tracking

Binds a rider to a vehicle under a weekly schedule (≈$70/week toward a ≈$4,900 lease-to-own price). Each weekly USDC payment is split deterministically on-chain in basis points — principal toward ownership, a yield slice to investors, and a platform/maintenance portion. Ownership progress is derived as a monotonic percentage and exposed for the UI's progress bar; an arrears counter drives configurable default handling. The payment atomically calls the yield distributor and credit registry.

5.3 yield_distributor — automated, O(1) pro-rata yield

Rather than looping over shareholders, distribution uses an accumulator: each payment increments a single accumulated-yield-per-share value, and an investor's claimable amount is computed lazily as shares × accumulator − reward-debt. This keeps distribution constant-gas regardless of investor count — thousands of investors per vehicle cost the same as one. Payouts are issued as Claimable Balances so yield is a first-class, auditable ledger object the investor redeems on their own schedule.

5.4 savings — Target & Lock accounts

Goal-based Target saving and time-locked Lock saving in USDC, with an early-withdrawal penalty enforced in-contract against the ledger timestamp. Balances can be optionally routed into DeFindex yield indexes (§9) so idle savings beat local inflation.

5.5 credit_registry — portable, oracle-ready credit

An append-only, write-gated history — only the lease contract's authorization can record a repayment — turning on-time behaviour into a mobility-based credit score. Exposed as an oracle-ready view that other lenders (and 3riKE's own product via Blend, §9) can consume, giving previously "unbankable" riders a verifiable financial identity.

6. Anchors & On/Off-Ramps — GHS ⇄ USDC

To let riders and investors move between local money and USDC with familiar rails (mobile money, bank transfer), 3riKE integrates Africa-facing Stellar anchors across the full SEP ramp stack:

  • SEP-10 — a challenge/response handshake where the anchor issues a specially-formed transaction the user signs (never submitted to the network) to prove account control; the returned JWT authenticates all subsequent anchor calls and seeds the app session.
  • SEP-38 — firm quotes with a quote ID and expiry, so the exact GHS↔USDC rate is shown and honoured before the user commits.
  • SEP-24 — hosted interactive deposit/withdrawal: the anchor serves its own KYC + payment UI in an embedded session, insulating 3riKE from handling sensitive PII and payment credentials.
  • SEP-6 — programmatic deposit/withdrawal for streamlined, returning flows where the anchor supports it.
  • SEP-12 — structured KYC field exchange with the anchor, reused to bootstrap 3riKE's own verification tier and reduce repeat KYC.

7. Bridge (Stripe) — Stablecoin Orchestration

3riKE integrates Bridge's Stablecoin Orchestration API for robust fiat↔USDC flows and future cross-border capability (diaspora investors funding riders, regional expansion). Anchors cover in-country mobile-money rails; Bridge adds card/bank funding and cross-border USDC settlement. Bridge webhooks reconcile into the same unified ledger as anchor events, so the app presents a single, consistent money-movement history regardless of provider.

8. Native Money-Movement Primitives

Beyond anchors, 3riKE uses Stellar's ledger primitives directly for transparency and atomicity:

  • Claimable Balances (CAP-23) — investor yield and lease refunds are escrowed as first-class ledger entries with claim predicates: a yield payout claimable unconditionally by the shareholder, or a refund that is time-bounded/conditional. Balances are auditable and reclaimable if unclaimed — ideal for transparent payouts and reversible escrow.
  • Path Payments — PathPaymentStrictReceive/StrictSend let a rider spend USDC while a counterparty receives a different asset, routed atomically through Stellar's native DEX and Soroswap liquidity, with slippage bounds. Single-transaction FX, no separate swap, no intermediate custody.
  • SEP-31 — direct anchor-to-anchor cross-border transfers for diaspora → rider funding corridors.
  • SEP-7 — signed payment-request URIs, so a rider or investor can be handed a link (in-chat, SMS, WhatsApp) that opens a pre-filled, verifiable payment — the chat-native money request.

9. Oracles & DeFi Composability

Reflector oracle

3riKE consumes Reflector, a decentralized Soroban price-feed network, for verifiable GHS/USD FX (last-price and TWAP) to price on-ramp conversions, value savings balances, and normalise investor returns. Its subscription model pushes updates for the pairs 3riKE depends on, and its on-chain feed means valuations are verifiable, not trusted.

DeFindex · Soroswap · Blend

  • DeFindex — routes Target/Lock savings into yield-bearing USDC index strategies so idle balances earn and preserve purchasing power.
  • Soroswap — aggregator/AMM providing the liquidity and best-path routing that powers in-app conversions and Path Payments.
  • Blend — a Soroban lending market; using verifiable credit_registry history, riders unlock under-collateralised micro-loans (repairs, batteries, emergencies), extending 3riKE from lease-to-own into full mobility credit.

10. Compliance & Asset Controls

Real-world asset finance in a regulated market (Ghana) requires issuer-level controls, which Stellar provides natively:

  • Trustline authorization flags — the 3RIKE-SHARE ownership asset is issued with AUTH_REQUIRED / AUTH_REVOCABLE, so only KYC-approved participants can hold ownership shares and access can be revoked if compliance demands.
  • Clawback (CAP-35) — enabled on the share asset so shares can be recovered in cases of fraud, chargeback, or a reversed lease — essential for RWA integrity.
  • SEP-8 regulated assets — for flows needing per-transaction issuer approval, an approval server can co-sign only compliant transactions.
  • Settlement asset — USDC is Circle-issued and Stellar-native: fully-reserved, compliant, and directly redeemable, so 3riKE never relies on synthetic or bridged stablecoins.

13. Security Architecture

  • Sovereign keys — AES-256-GCM under a PBKDF2 (600k-iteration) key; only the encrypted blob, IV, and salt are stored; decryption is in-memory during signing only.
  • Gas abstraction — fee-bump envelopes; users never hold or spend XLM, removing a whole class of failure and phishing.
  • Least-privilege authorization — every Soroban invocation carries a scoped authorization tree; the fee sponsor can pay fees but can never move user funds.
  • Webhook integrity — anchor/Bridge callbacks verify the provider signature and a ±5-minute timestamp window (replay protection) before any ledger-state mutation.
  • Issuer controls — trustline auth flags + clawback on the share asset provide a compliant recovery path for RWA edge cases.

14. Testing & Assurance

Contracts are developed test-first with Soroban's native testing framework, which runs invocations against an in-memory ledger with controllable time and mocked authorization — enabling deterministic simulation of multi-week lease schedules, yield distribution across many investors, penalty/early-withdrawal paths, and default handling. Deployment and invocation are driven on Stellar Testnet, with a CI pipeline running the contract suite plus TypeScript integration tests end-to-end on every change. A dedicated security-review pass precedes any mainnet deployment, and the issuer's clawback/auth controls provide a safety net for early production.
